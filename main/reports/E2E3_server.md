### 1.2 E2 M1 (DINO-WM PushT)

1. **DP rollout**(`e2_dp_rollouts.py`)
   - checkpoint 24개(seed 42·43·44 × epoch 20·25·30·40·50·80·220·1000, EMA)를 DINO-WM 환경에서 돌렸다. 초기 상태 seed 100000~100099를 모든 checkpoint가 공유한다(짝 설계).
   - 프로토콜은 E0 그대로다: DP 초기 상태 공식, n_obs 2, n_action 8, DDPM 100, coverage > 0.95거나 300 step이면 끝.
   - DDPM 잡음 seed는 checkpoint마다 같다(torch seed 0).
2. **모드 O 창**(`e2_dp_windows.py`)
   - episode마다 H ∈ {3, 5, 7, 10}에 대해 마지막 5H 제어 step을 창으로 삼았다. 시작 관측은 실제 1프레임 + proprio다.
   - 기록한 상대 행동으로 DINO-WM을 open-loop로 굴렸다. 같은 창의 실제 최종 프레임과 상상 최종 프레임에 a_std 앙상블(E1 고정, 표준 목표 프레임)을 적용했다.
   - 참값은 실행한 episode의 기록 최종 상태의 r_obj다.
   - T_end < 5H라 앞을 0 행동으로 채운 창은 H10에서 1개뿐이었다.
3. **통제**(`e2_ctrl.py`): R2-12 main 집합(val, H5, 400 episode, seed 303, 교란 정책 8개 + 전문가)을 E1 판정기로 다시 판정했다. E0 재현 파일과 달성 r이 3,600궤적 모두 같다.
4. **분석**(`e2_m1_analyze.py`, `e2stats.py`, CPU): 정책 수준 양, 순위 지표, H2 판정, bootstrap 10,000회, 순열 검정 10,000회

### 1.3 E2 M3 (R2-9 통제 장면)

- E1 모델 9개(p ∈ {0.03, 0.1, 0.3} × seed {0, 1, 2})로 R2-9 정책 π1~π6을 R2-9 평가 bank(시작 장면 1,024개, seed 12345)에서 평가했다(`m3/m3_e2_eval.py`).
- 장면마다 상상 최종 프레임과 실제 f4의 고정 판별기 logit, 실제 r을 저장했다.
- 겹치는 E0 모델 5개의 정책별 상상 성공률이 E0와 정확히 같다(차이 0.0).
- 분석은 `m3/m3_e2_analyze.py`(CPU)다.

### 1.4 E3 (M1의 판정기 × 입력 분해)

- (a)·(b)는 E1 곡선 집합 16칸의 기록(실제·상상 판정)을 그대로 쓴다. DP 집합은 E2 창의 a_std 판정이다.
- (d)(VLM)는 새로 돌렸다.
  - VQ-VAE decoder: DINO-WM 체크포인트 안의 decoder(10.1M)다. 실제와 상상을 모두 DINOv2 특징에서 224 px로 되돌린다(`declib.py`).
  - E1 곡선 집합은 특징을 저장하지 않았다. 그래서 val H5의 r·r_obj 칸을 같은 seed로 다시 생성했다(`e3_regen_e1.py`). a_full·a_obj 앙상블 출력이 E1 기록과 반올림 오차(5e-7) 안에서 같고, 달성 r은 정확히 같다.
  - 규칙 집합(`e3_rules_dset.py`, `e3_rules_std.py`)은 E1 판별기 학습 집합과 a_std 학습 프레임을 같은 seed로 다시 만든 것이다. 구간 비율·held-out 수가 E1과 정확히 같다.
- 분석은 `e3_d_rules.py`, `e3_m1_analyze.py`(CPU)다.

## 6. 편차와 결정이 필요한 것

### 6.1 편차·사고(모두 기록, 결과에 영향 없음)

1. **DP 창 재생의 정확 일치 점검 실패**
   - 다른 프로세스에서 다시 재생하면 pymunk 접촉 순서가 달라질 수 있다. 한 episode에서 최종 block 위치가 2.4e-3 px 어긋났다(r_obj 차 1.2e-4).
   - 참값은 원래 정의대로 실행한 episode의 기록 최종 상태로 하고, 창 프레임을 그리는 재생과의 차이를 창마다 기록하도록 고쳤다.
   - 전체: 최대 0.0041 px, 1e-6 px 넘는 창 4개/9,600, 구간이 바뀐 창 0개
2. **VLM 환경**
   - download.pytorch.org가 서버에서 시간 초과됐다. 그래서 PyPI의 torch 2.7.0(CUDA 12.6 빌드)을 썼다. M2는 2.7.0+cu128이다.
   - flash-attn 대신 SDPA를 쓰고, 가중치 일부를 CPU에 두었다(v2.2 §7에 허용된 범위).
3. **VLM 재시작**: 처음에는 batch 32, GPU 9GiB로 시작했다. DP 창 작업이 끝난 뒤 batch 64, 11GiB로 다시 시작했다. 첫 실행의 부분 결과(1,024쌍)는 쓰지 않았다(`vlm_v1_partial/`). 모든 점수는 한 설정에서 나왔다.
4. **(d) dset 규칙 집합에 전문가 행동열이 들어 있다**(확정된 정의 그대로). 뺀 값(0.629, 0.691)도 기준에 못 미쳐 판정이 같다.
5. **분석 출력 오류**(E3 분석의 출력 줄 KeyError). 출력 부분만 고쳤고 계산에는 영향이 없다.
6. **GPU 메모리**: VLM 실행 중 GPU 1은 최대 약 20.2GB(A 7.4GB + B 12.7GB)였다. B GPU 작업은 늘 2개 이하였고, GPU 0은 쓰지 않았다.
7. 판정 성공은 앙상블 확률 > 0.5로 셌다(E1 코드와 같음; 설계 문구는 "≥ 0.5"). 정확히 0.5인 값은 없다.

### 6.2 결정이 필요한 것

1. **M1의 H2 서술**: 표준 지표가 좋게 보이는 조건(H2c)만 성립한다. 기하 법칙(H2a 0.357)과 순위 역전(H2b)은 a_std 판정 칸에서 나타나지 않는다.
   - 원인은 "near-miss 오판 3배(0.06 → 0.19)이지만 정책 수준 편향이 0.06 이하"다.
   - 판정기를 VLM으로 바꾸면(보조, 4.3절) 순위 역전 쌍이 나타난다. 논문에서 이 민감성을 어떻게 서술할지 정해야 한다.
2. **M3의 H2b**: 조건 쌍 2개(상상 차 27%p, 41%p)가 있다. 그러나 τ_b가 1.0이라 불성립이다. 원인은 π4·π6의 실제 차가 0.5%p로 사실상 같은데, 그 우연한 순서가 상상 순서와 같은 방향이라는 것이다.
   - 사전등록 기준대로 불성립으로 보고한다. 서술에서 이 한계(τ는 방향만 본다)를 밝힐지 정해야 한다.
3. **H3의 M1 결과(0.239)와 보조 칸의 차이**: 원 정의 r에서는 지각 바닥(agent 위치가 지배하는 near-miss)이 커서 불성립이다. 물체 자세 정의와 DP에서는 상상 몫이 0.57~0.80이다. 정의별로 나눠 서술할지 정해야 한다(v2.1 §6의 "정의마다 따로 보고" 원칙과 같은 방식).
4. **VLM 가중치와 환경 보관**: Qwen 가중치 16GB(`~/pmx/hf`)와 `b-vlm` 5.5GB를 남겨 두었다. 다음 단계에서 (d)를 쓰지 않으면 지워도 된다.
